# Event 1.0.8 配套脚本：三倍奖励、料理保底与大奖

当前 Forge 1.20.1 实例的许愿井新规则。只修改服务器许愿井和客户端提示两份脚本；Event、Boss、价格模组的 JAR、价格表和其他经济逻辑不变。

## 正式规则

- 绿宝石和金币锅两个许愿池，除武器及法术卷轴外，普通实物奖励数量为原来的 **3 倍**。例如矿物块原来 1～2 个，现在 3～6 个；金币袋原来 1～9 个，现在 3～27 个；晶球、技能经验书、种子袋原来 1 个，现在 3 个。庄园唱片也按实物增加。
- 有用实物每次有 **1%** 概率中数量大奖，在三倍奖励上再乘 **10**，即普通基数的 30 倍。杂物和粪便仍三倍，但不出现虚假的“中大奖”提示；落空不变。
- **武器和法术卷轴不增量、不进入数量大奖，掉率不变。** 原生类别签池、矿物稀有度子池不改；庄园综合奖励仍合计 0.035%，其中原有武器/唱片/法术抽取方式不改。
- 食物扩为 **32 种**已核对实际模组物品模型、且有正出货价格的料理；每次随机给 **3 种不同料理**。
- 每次料理按 `global.getItemPrice` 的普通品质单价，扣除当前市场折价后向下取整，补足数量使总价值 **至少 1000 金币**。只保守计折价，不把涨价、技能加成或未来售价算入保底。价格表变化会在下次许愿时动态读取，不改价表来伪造价值。
- 料理数量大奖为同份礼包再乘 10，保底估值至少 10000。所有大量奖品都按实际物品最大堆叠数量分组发放，背包放不下时由原有 give 路径明确掉落，不给超大非法堆叠。

“3 倍”指原数量 ×3，而非额外 +3 倍；“至少 1000”指每次食物事件的整个三菜礼包，而非每一道单独 1000。

## 支付和性能

- 两个池都先生成、验证整份奖励，再支付/保存进度，再发奖。食物价格 API 缺失、有效料理不足 3 种、存档失败时，不收费或回退原支付，不重抽成其他类别。
- 原本绿宝石先收费再生成奖励的路径改为先准备；这不是只提高提示文字或 UI 数字。
- 一次整叠 64 锅先检查全部奖励；32 种料理的当前价格只计算一次，复用到本批次，避免 2048 次市场状态查询。
- 原有背包捕获/恢复修复保持。打开商店期间不消费金币锅，绿宝石也不把奖励发进被捕获的背包。

## 保持不变

- 累计 64 绿宝石块解锁、首锅抽奖和旧版解锁资格。
- 商店：非庄园召唤物 1 金币锅、随机庄园武器 5000 万（排除万味胚刃）、随机庄园法术卷轴 500 万（不含常规铁魔法）。商店出售物品不参与三倍或数量大奖。
- 四向放置、天气、Boss、价格表、世界存档与 NeoForge 实例均不改动。
- 未改原生金币池的基数；实际金币直接返还期望由原 25 金币/锅提高到 25×3×1.09 = 81.75 金币/锅，不含其他可出售物品价值。

## 验证与复现

候选和实际安装文件行为回归均为 **1756 通过，0 失败**。测试包含普通三倍、精确 1% 数量大奖边界、武器/卷轴保护、32 种价格核对、四档折价下每次三菜 >=1000、整叠 64 锅、满背包掉落、存档失败退款、两种投入方式，以及庄园商店和升级回归。测试执行未修改的完整出货价脚本获取真实价格 API，另核对所有料理基础价格一致。

实际安装 JAR 的原生验证器还遍历 100000 个类别签、10000 个矿物签，确认庄园综合奖励仍为 0.035%，12 种矿物稀有度和原生抽奖数量均未改动。

相同的实际发奖入口验收指向本轮修改前的原脚本，5 项按预期失败，证明原版实际发放没有三倍、大奖或食物保底。保留不可变旧版参考文件；首锅抽奖计数回归的模拟奖励改用不增量的庄园武器，另行用新测试覆盖实物增量，未把当前代码伪装成原版通过。

- 已安装文件：上述命令后追加 `--instance` 和实例绝对路径。
- 负对照：追加 `--baseline`，预期退出码 1。
