# 食物武器：构筑、成长与修复

本页面向食物武器、石像交互和兼容接入的维护者。从 [架构总览](../ARCHITECTURE.md) 进入，返回 [总导航](../README.md)。部署证据与验证资料统一从 [参考目录](../REFERENCE_INDEX.md#正式交付与验证入口) 查阅。

## 系统职责与适用范围

食物武器系统让同一件武器持续经历材料构筑、食物配件配置、进化、磨损和石像修复。构筑、成长和实际使用共用武器身份与服务端规则，不能各自保存一份互相冲突的状态。

全部武器兼容清单都在维护范围内，包括清单中的原生武器、铁魔法、三叉戟和首领相关武器接入；磨损与修复规则不得以排除其中某类武器的方式缩小范围。清单外的新物品仍需独立适配，不能仅凭外形、名称或同属某个模组就认定兼容。

“属于兼容清单”和“参与磨损”是两个判断。磨损要求食物武器原生可损坏且已经纳入服务端管理；绑定石像或改件等正常流程建立管理记录，不以已经成功进化为前提。原生不可损坏、无限耐久以及只使用法力或自定义能量而无原生耐久的武器自然不满足资格，不为它们补造虚拟耐久，也不因此从兼容清单中删除。

这里不复制每种材料的倍率、格子权重、技能数值或网络字段。具体规则与接入名单请按末尾的源码入口定位。

## 模块如何分工

| 模块 | 负责什么 | 必须守住的边界 |
| --- | --- | --- |
| 基础结构与原生材料表示 | 保存、评估各武器结构、原生材料表示及可编辑范围 | 展示格和配方成本不是可重复领取的实物 |
| 材料目录与材料能力 | 识别允许的材料，计算构筑贡献，承接材料被动 | 不修改独立价格系统，不凭物品名称推断兼容性 |
| 食物配件与进化 | 管理配件、进化状态、技能装载和稀有度记录 | 查询或重新打开界面不能重新抽取已保存收益 |
| 原生磨损与使用门禁 | 识别受管武器、结算阶段、移除可舍弃部件、限制耗尽使用 | 不改造原本没有耐久的武器，不以磨损破坏必要核心 |
| 石像任务与修复 | 受理任务、记录交付、确认领取并恢复满耐久 | 补装不是修复，其他修复入口不能绕过任务 |
| 容器、界面与网络 | 呈现状态、接收操作意图、服务端校验与结果同步 | 客户端没有材料扣除或武器写入的最终权限 |
| 具体武器、原生行为与集成 | 执行对应攻击、投射、施法、技能及表现 | 保持各自来源和结算边界，不另起一套脱离共享状态的规则 |

## 状态与权限属于谁

武器的身份、构筑、绑定、进化和技能记录随物品保存。原生磨损还在服务器世界中保留权威记录，用于确认已结算阶段、磨损状态和修复任务的实际交付。物品显示、客户端镜像或重新打开的界面不能替代这些记录。

修复任务跟随具体武器，而不是某个临时面板。服务端检查当前武器身份、修订、绑定类别、实际库存、玩家状态与交互位置，再决定操作是否成立。进化或实际退级等使任务依据失效时，不能沿用旧支付进度。

原有配方成本、原生材料布局和玩家付费放入的部件是不同概念。布局不能成为重复收费或返还原生材料的依据；真实放入的部件必须按实物编辑和结算。

## 构筑与成长流程

玩家在石像入口查看武器结构，服务端容器处理真实材料的放入、移动、替换和取出。剑腔按单格单件表达部件；其他武器由对应基础结构处理，不强行套用剑的布局。

材料变化需要兼顾武器结构与已有损耗。补充材料、更换配件或重新计算容量均不会恢复耐久，也不会重置已经结算的磨损阶段。

进化由服务端读取成长状态与供品条件，完成合法消耗后更新同一武器。取得技能时保存稀有度记录，重复查看不重抽。稀有度只参与规定技能的计算，不表示所有伤害、治疗和增益一概放大。

## 磨损如何推进

### 阶段与部件选择

剩余耐久首次达到或低于 50%、35%、20%、10% 时，分别结算对应阶段；每个阶段只结算一次。一次原生损耗跨过多个阈值时，依次处理尚未结算的阶段。

每次从可安全移除的非必要部件中，优先移除最低稀有度的部件。核心部件以及维持武器合法性所需的结构不参与移除；没有合适部件时，不为凑足脱落数量而拆掉必要核心。脱落不是取出或退款。

阶段记录与剩余耐久一同受服务端约束，不能通过补装、换件或反复打开界面重新获得未磨损状态。具体阶段定义与选择规则由 `NativeFoodWeaponWear` 及对应结构适配器维护。

### 耗尽与不参与磨损的武器

受管武器耗尽后仍保留物品，攻击、挖掘、普通使用和技能入口受使用门禁约束；允许的石像管理与修复入口不能一起被封死。暂时无法使用、结构不合法和存档损坏也不是同一种状态。

无限耐久、不可损坏以及只消耗法力或自定义能量的武器保持原行为：不创建虚拟耐久，不结算部件脱落，不施加这套石像修复限制，也不附带额外使用、附魔或能量副作用。未绑定、未改件的普通原生耐久武器同样不会仅因存在于背包中就被接管。

## 为什么必须通过石像修复

对已经纳入磨损的武器，经验修补、铁砧修复、合成修复、物品修复和附魔灌注台修复都不能恢复耐久。限制针对修复结果，不影响普通附魔、改名或正常经验获取，也不借阻止修补吞掉经验。

石像按武器的绑定类别受理任务。玩家分项交付要求的材料，服务端从真实库存扣除并记录支付；数量按当前任务规则确定，不把验收样例的用量固定为所有任务的常量。全部条件满足并成功领取后，武器一次恢复满耐久，不采用分次补装恢复的方式。

任务领取、任务失效与满修提交属于同一受控过程。旧请求、旧进度和已经领取的结果不能再次生效。满修保留原生磨损的管理身份（`Identity`）和已结算阶段位图（`Mask`），不通过重建身份或清空阶段再次获得未磨损状态，也不补回已经脱落的部件；武器结构是否可用仍由结构规则判断。

## 既有战斗与兼容边界

磨损与修复使用既有权限与结算体系，不替换伤害、效果或原生行为的权威入口。下表用中文说明维护时常见的几个边界名。

| 边界 | 保持的职责 | 与磨损、修复的关系 |
| --- | --- | --- |
| 状态权威（Owner） | 确认来源、当前武器状态和获准写入的范围 | 阶段和任务不能由界面或任意数据改写自行授权 |
| 最终伤害（Final） | 协调同一次攻击的最终伤害与获准效果 | 不以磨损附加第二条伤害结算链 |
| 结果消费（Consumer） | 只在当前动作的授权范围内应用已确认结果并完成收尾 | 取消、失败或过期的授权不能被重新应用 |
| 原生接入（Native） | 承接原有攻击、发射和命中路径 | 在真实耐久变化上结算磨损，不为无耐久武器造损耗 |
| 铁魔法（Iron） | 保持原有施法来源、会话和效果接入 | 纯法力武器不会因此变成耐久武器 |
| 三叉戟 | 保持投掷物、原物品与伤害来源的关联 | 不用无关副本冒充当前武器的合法状态 |
| 首领（Boss） | 保持首领战斗、武器被动和奖励各自的边界 | 不因武器磨损修改首领规则、接管独立事件模组或扩大权限 |

这些边界与兼容清单保持有效，但不等于所有武器都会触发磨损。原生不可损坏者按资格自然排除；纯法力或纯能量也不能成为人工补造耐久的理由。

## 失败时从哪里排查

| 情况 | 处理边界与阅读方向 |
| --- | --- |
| 武器没有进入磨损 | 先查原生耐久、不可损坏标记以及绑定或改件状态，不先补造耐久 |
| 阶段没有部件脱落 | 先查阶段是否已结算，以及是否存在可安全移除的非必要部件 |
| 常规入口不能恢复耐久 | 对受管武器这是修复边界；普通附魔、改名与经验获取仍应保留 |
| 石像修复未完成或领取失败 | 查真实交付、武器身份与修订、绑定类别和任务是否仍有效，不直接改耐久字段 |
| 请求过期或容器提交失败 | 不能按旧面板提交；核对真实库存、武器状态及失败应答，不只纠正界面 |
| 原生行为、法术或首领效果异常 | 沿原有来源、最终伤害与结果消费链查找，不绕过权威校验补发效果 |

## 性能与正确性边界

基础规则规范摘要由 `FoundationCanonicalDigest` 生成。优化仅改变其中私有字符串编码的字节批量写入，保持严格 UTF-8 编码、非法代理字符的异常、规范字节顺序和预算检查；不会缓存可变授权、跳过来源校验或扩大石像支付与满修权限。首领、法术、奖励、网络入口及注入配置不属于这项优化的改动范围。

Spark 性能分析工具的同条件单次配对采用相同探针、世界来源与模组组合，仅替换首领模组包。这里记录的是受测流程的实际墙钟耗时：

| 受测流程 | 基线耗时 | 当前包耗时 |
| --- | --- | --- |
| 原生绑定磨损固定负载 | 40084 毫秒 | 31400 毫秒 |
| 真实石像付费满修流程 | 246373 毫秒 | 223743 毫秒 |

这些是单次配对观察，不是玩家帧率、全服性能或统计显著性结论，也没有证明首领整体提速。冷启动早期存在后台干扰，首领阶段还披露了基线侧的一次诊断接入，不能据此宣称启动或首领战斗普遍加速。原始采样与具体限制统一从参考目录查阅。

规则快照重算、规范序列化与受保护的别名访问仍有明显开销。进一步优化必须保留操作来源、当前规则和实际支付的校验，不能通过持久缓存授权结论或绕过保护换取速度。

## 未完成与待确认

仍需真人确认界面比例与交互、完整进化和维修长流程、全部首领技能与被动、多人同步及长期体验。选定首领的短程运行不替代这些验收。

全局外部继承关系的完整证明仍未建立；静态检查的 5458 项未解析引用与 `ManorSpellRules` 既有访问标志警告不能视为已消除的兼容风险。残余规则快照与别名访问热点仍需独立调查，不把有限优化写成全部性能问题已经解决。
