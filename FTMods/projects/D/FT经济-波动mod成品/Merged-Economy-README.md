# FarmingTales 财富波动＋卡顿波动合并版

成品：`qys-economy-merged.jar`，版本 2.0.24。一个 jar 同时提供 `ftecon` 与 `ftlagcontrol` 兼容标识。

## 2.0.24：补齐 Refined Storage 的 Observable / 本地耗时检测

- 已按实例中的 **Refined Storage 1.12.4 / Observable 4.4.2 / Forge 1.20.1** 实现。RS 在 `NetworkListener.onLevelTick` 的世界 END 事件中分别更新网络和网络节点，不经过原版方块实体 ticker；原 OBS 的 ticker 计时覆盖不到这里，单纯把 RS 加进普通机器白名单不能解决。
- 在原 RS 监听器调用 `INetwork.update()` 和 `INetworkNode.update()` 的位置包裹真实纳秒计时。控制器的网络维护/同步合成管理耗时归到控制器位置；Importer、Exporter、Interface、Crafter、外部存储等由此监听器更新的节点归到节点自己的维度和区块。各次更新只调用原方法一次，不额外枚举网络。
- 运行一次 OBS 采样后，数据直接写进 OBS 原有的方块计时表，带真实 RS 方块名称、位置、累计纳秒及更新次数，供原界面叠加、报告和已有报告监听器使用；不是伪造一个固定 μs 数字。更新抛异常也在 `finally` 关闭计时并还原 OBS 当前目标，不吞掉 RS 自己的异常。
- 不开 OBS 时仍进入本模组本地实测；关闭区块管控后仍可单独做 OBS 采样。关闭管控且 OBS 未采样时跳过计时。OBS 没装时保留本地实测；RS 没装时跳过兼容 Mixin，两者都不是新增必需依赖，不打进成品。
- RS 实测沿用 2.0.23 的 **FTB 团队认领区块跨维度总 μs/tick** 汇总。OBS 与本地实测同一区块仍取较大值，不把同一次 RS 更新相加两遍。
- 本次**只补 RS 检测，不新增 RS 断网、停止网络更新或库存没收规则**；RS 存储节点不加入通用生产库存快照/没收白名单，原有物品不因检测而被扫描或扣走。团队超线后的原有区块处罚、交互限制和其它生产机器管控仍按原配置运行。

### 使用与排查

1. 停服，备份后替换原 `qys-economy-merged.jar`，不要并存新旧两个版本；OBS 和 RS 保持原有 JAR。本地测试和成品交付不自动改动正式存档或安装目录。
2. 在服务器用 OBS 原界面或 `/observable run 30` 启动采样，采样期间让实际的 RS 导入/导出/合成运行；结束后查看对应 RS 方块上的 μs。
3. OP 用 `/lagcontrol observable` 查看 RS 的“已实测更新次数 / 写入 OBS 次数”和两处兼容注入自检；`/lagcontrol observable 10` 也可沿用原有自检采样入口。不开采样时“写入 OBS 次数”不增加属于正常情况。
4. 团队生产限制仍等待原统一评估窗口（默认 24000 tick），不是每次采样后立即处罚。RS 条目没有真实更新或几乎空闲时，不能把接近 0 μs 当作兼容失效。

### 性能与统计边界

- 在 RS 原有更新循环内 O(1) 包裹调用，本地实测每次两次 `nanoTime` 加原有区块 HashMap 累计；计时帧按调用深度复用，不为每次原生计时新建帧，不缓存/扫描所有网络或库存，不在更新热路径查询 FTB。
- OBS 条目、调用目标和报告的维护仅在**主动采样期间**发生；每个位置首次建条目时读已加载区块的方块名，使用 `getChunkNow`，不为检测强加载区块；非服务器线程跳过，避免异步写服务器计时表。
- 覆盖上述服务器主线程 RS 网络/节点更新及其同步子调用，**不声称覆盖异步合成规划、玩家网络包、其它模组单独触发的所有存储查询或整个服务器 MSPT**。这些时间不凭空归给某个 RS 区块；储存网络跨团队连接时，各节点按实际执行位置归属，控制器共同维护开销仍归控制器所在地。
- 开发用本地 `libs/refinedstorage-1.12.4.jar` 来自用户实例。常规构建：Java 17 下 `gradle --offline build runGameTestServer`；`-PgameTestNamespaces=ftlagcontrol_rs -PwithoutObservable` / `-PwithoutRefinedStorage` 为可选依赖兼容启动验证，缺少对应模组时跳过依赖该模组的用例，不把跳过冒充真实负载验证。

下面保留 2.0.23 的团队总量规则，仍然有效。

## 2.0.23：按 FTB 团队认领区块总耗时限制生产

本节为当前生产管控口径；后续旧版本章节保留作历史记录。与用户提供的 2.0.22 成品比对 SHA-256 完全一致后，在对应源码上修改，不涉及 ftboss。

### 判定与作用范围

- 每个统一评估窗口读取一次 FTB Chunks 认领快照，以 FTB Teams 团队 UUID 分组，将同一团队**所有维度**有有效采样的认领区块平均耗时相加，作为团队总 μs/tick；**不除团队人数、在线人数或区块数**。
- 同一窗口内原有机器实测与 Observable 的合并方式不变：同一区块两份证据取较大值，不重复相加。合计仍限于原模组已覆盖的实测来源，不代表所有第三方异步负载都已被测到。
- 示例：同一团队两个区块分别 450 μs/tick，团队总计 900；虽然两个单区块都不足 800，团队仍达到默认冻结线。不同团队不互相累计。
- 该总量决定**该团队全部认领区块**的限产/冻结，包括本窗口没有机器采样、空闲或未加载的认领区块。未加载区块只登记限制，不为检测或清场强制加载。
- 默认仍为 500 μs/tick 起限产、800 全额没收/冻结；沿用配置中的实际阈值、评估间隔（默认 24000 tick）及连续样本数，不擅自改玩家手动配置。连续样本按团队累计一次，不按该团队有几个区块累计。
- 未认领区块保留单区块规则。FTB 不存在或认领接口暂不可用时明确显示回退单区块判定，不凭空猜测归属；已有红色冻结不会因此消失。
- 认领转移/取消按下次统一评估的最新快照处理。黄色限制可恢复，红色冻结继续随区块存档保留，认领转移不自动解冻，须管理员处理。

### 处罚与解除

- 沿用既有冻结停止机器、禁止交互、清场配置。**注意：原默认冻结清场会移除受影响已加载区块的掉落物与非 boss 生物（包括命名/驯服生物，除非另开保护）**；这次团队范围扩大后，该规则也覆盖该团队其余被冻领地。玩家、boss 与旧机器库存仍按原规则保护。
- 同队一次评估只通告一次；冻结后仍达到团队总量冻结线，踢人/通告/升级冷却按团队执行一次，不会每个领地区块重复踢同一批成员。
- `/lagcontrol release` 仍只解除目标区块。该区块在保护期内不受新处罚，但其实际耗时仍计入团队总量，防止通过局部解除稀释其他领地的判定。
- 新增 `/lagcontrol releaseteam`：玩家站在该团队任意认领区块内，解除这个团队当前所有维度的认领区块限制，并给予既有解除保护期。
- 新增 `/lagcontrol releaseteam <团队UUID>`：从任意位置或控制台解除指定团队领地。两个命令均需权限等级 2。历史已取消认领的红冻区块仍用旧的逐区块 release 解除。
- `/lagcontrol` 显示生产限制口径与回退状态，`/lagcontrol list` 中同队各区块显示同一团队总耗时，**不要把这些行再次相加**。
- 原财富、堆量行情、出货箱账本、独立的“每日团队人均收入扣减”保持不变；`/lagcontrol teams` 仍是每日收入扣减看板，不是本次新增的总量生产限制看板。关闭 `teamPenaltyEnabled` 不会关闭团队总量生产管控，后者仍由 `enabled` 控制。

### 性能与验证

- 新增分组仅在原统一评估时执行，时间/内存复杂度为 O(采样区块 + 认领区块)，不在机器 tick、玩家 tick 查询 FTB 或遍历领地。
- 生产冻结热路径继续直接查原来的区块 HashMap；边界粒子每位玩家每 40 tick 最多查附近 49 个区块、显示 4 个，不再遍历全部限制记录；未加载区块跳过清场。
- 纯规则覆盖团队跨维度总和、独立团队、未认领回退、空闲领地、非法/无穷输入、总和溢出保护、无证据处理。
- 真实 FTB Teams/Chunks 集成覆盖两队跨维度认领、团队连续样本、离线队伍同样受生产限制、未加载区块不强载、冻结持久化、同队升级去重、单块/整队保护期、领地转移与黄色恢复；同时回归原 Observable/Create/KubeJS/财富/SDM 测试。
- 构建使用 Java 17 / Forge 47.4.10；完整测试在独立 GameTest 世界运行，不打开正式存档。本次不新增客户端网络或必需依赖，FTB 保持可选反射接入。

## 2.0.21：区块实体规则（同种生物上限 / 800 μs 冻结 / 冻结禁交互 / 冻结清场）

### 一、同种生物上限：一个区块内同一种生物超过 5 只，多出来的直接消失
- 每 100 tick（5 秒）扫一次，按「区块 + 生物种类」分组，超过 `entityCapPerChunk`（默认 **5**）的部分直接 `discard()`：
  **不掉落、不给经验**（否则清怪反而制造掉落物）。
- 保留最早生成的那几只（按实体 id）；玩家与 boss 不受影响；有名字/已驯服的生物默认放过（`entityCapKeepNamedEntities=true`）。
- 只统计生物，不统计掉落物（掉落物由第四条的冻结清场处理）。
- 日志：`同种生物上限（每区块每种 5 只）：本次清除 N 只（不掉落、不给经验）`

### 二、卡顿超过 800 μs/tick 直接冻结区块
- `freezeMicrosPerTick` 默认 **800**（原 2000），超过即冻结（`consecutiveSamplesBeforeFreeze=1` 时当场冻结）。
- 为了让「限产」这档仍有意义：限产起点降到 **500**、全额没收与冻结同一线 **800**；500–800 是黄色限产（按比例没收新增产出），≥800 直接红冻。
- 旧配置自动迁移（仅当数值仍等于上一版默认 1000/2000/2000 时改写，不动手动调过的值），`configVersion` → 3。

### 三、冻结区块禁止交互，直到管理员解除
- 冻结区块内**放置/破坏/使用方块**一律拒绝（右键、左键、`BreakEvent` 三道都拦），动作栏提示
  `该区块因卡顿已被冻结，无法交互；管理员可用 /lagcontrol release <维度> <区块X> <区块Z> 解除`（每玩家 2 秒最多一条）。
- 管理员（权限等级 2）默认可以照常操作，便于进区块维护（`frozenChunkOpsBypass=false` 可关掉豁免）。
- 冻结仍然只由管理员 `/lagcontrol release` 解除。

### 四、冻结区块时清场：全部掉落物 + 非 boss 生物
- 区块被冻结的当下（自动冻结、`/lagcontrol freeze`、以及「冻结后仍高卡顿」的升级处理）清除该区块内：
  **全部掉落物**（`frozenChunkClearDrops`）与**全部非 boss 生物**（`frozenChunkClearMobs`）；
  玩家与 boss 保留；有名字/驯服的生物默认**一起清除**（`frozenChunkKeepNamedEntities=false`，想保护宠物改成 true）。
- 清除为静默 `discard()`（不掉落物品）；日志：`冻结清场 <维度> 区块 [x,z]：清除掉落物 A 个、非 boss 生物 B 只`。
- boss 判定：类在 `net.farmingtales.ftboss` 包下，或实体 id / 类名里含 `boss`。

### 测试
- 纯逻辑：800 线上下、配置线硬下限 100（不再是 1000）、上限超出量、交互豁免（普通玩家 / 管理员 / 开关关闭 四种组合）。
- GameTest：区块内 7 头牛 → 上限过后正好剩 5 头；冻结区块 → 掉落物清空、普通牛清掉、命名牛按配置保留/清除、非管理员交互被拦。

## 2.0.20：删除 SDM 商店波动

按需求把「商店波动」整个删掉 —— 本模组**不再以任何方式改动 SDM 商店的价格**：

- 删除 `SdmShopPricer`（按财富上调商店买价的那套）及全部调用点：开服初始化、玩家登录、卖出入账后的刷新、
  财富开关切换后的全量刷新，并移除 `/lagcontrol shopbase` 命令与配置项 `shopMaxPriceIncreasePercent`。
- **保留一次性收尾**（`SdmShopRestore`）：2.0.16 及以前涨价会把结果写进 SDM 自己的商店数据，
  直接删功能会让价格停在「涨过」的状态；因此开服用当时记下的原价（存档 `shopBase`）恢复一次，
  之后 `shopRestored` 落盘、**永不再碰商店**。恢复逐条打日志：`商店价格恢复为原价：1300 → 1000（条目 …）`。
- **财富波动本身保留**：出货箱那边的单价乘区（财富档位 × 堆量行情 × 卡顿/团队乘区）不受影响，`ftprice`/`ft wealth` 照常。
- 测试同步改造：
  - 纯逻辑：`shopBase` / `shopRestored` 的存档往返 + 「恢复只做一次」语义；
  - `sdmShopPricesAreNeverTouchedByThisMod`（真实 SDM 商店条目）：打开财富开关、卖出入账之后，条目价格**保持整合包原值**；
  - `legacyShopPricesAreRestoredExactlyOnce`：收尾只执行一次，第二次为空操作。

## 2.0.19：冻结升级——冻结后还是卡就踢团队一次 + 全服通告 + 重新冻结

区块被冻结后，**下一次统一评估如果它仍然高卡顿**（说明冻结没能解决问题，通常是本模组管不到的机器或别的来源），执行升级处理：

1. **踢出认领该区块的团队在线玩家一次**（认领关系与圈地团队扣减用同一套 FTB Chunks 数据；区块没被任何团队认领就不踢人）；
2. **全服通告一次**：`区块 <维度> [x,z] 冻结后下一次检测仍然高卡顿（12345 μs/tick）：已重新冻结。团队「XX」在线 3 人已被移出服务器，修好机器后再进服。`
3. **重新冻结该区块**（刷新冻结时间戳与耗时记录）；冻结仍然只由管理员 `/lagcontrol release` 解除。

- 被踢玩家看到的原因：`你团队圈地内的区块被冻结后仍然高卡顿（…）：请先停掉那里的机器再进服；管理员可用 /lagcontrol release 解除冻结。`
- 配置（`config/ftlagcontrol.toml`）：
  - `freezeEscalationEnabled`（默认 **true**）总开关；
  - `freezeEscalationKickTeam`（默认 **true**）设为 false 就只全服通告、不踢人；
  - `freezeEscalationCooldownMinutes`（默认 **0**）同一区块两次升级的最短间隔，想温和些可设 60。
- 行为保证：**冻结绝不会被自动解除** —— 该区块之后即使变安静，也只保持冻结（既有测试同样钉住了这一点）。
- `/lagcontrol` 新增一行：`冻结升级：开启（踢团队 + 全服通告 + 重新冻结）（已执行 N 次）；/lagcontrol freeze [~ ~] 手动冻结、release [~ ~] 解除`
- 测试：5 项纯逻辑检查（只有「已冻结 + 仍高卡顿」才升级、冷却生效与过期、首次检测不升级、冻结有效不升级）
  ＋ 真机 GameTest（真实 FTB 认领：冻结 → 仍高卡顿 → 升级 1 次并重新冻结；之后变安静不自动解除；未认领区块没有可踢的团队）。28 项测试全绿。

## 2.0.18：玩家本身不计入区块卡顿（可见 + 可配置）

「区块卡顿」盯的是机器，不该把站在那儿的玩家算进去。这条规则本来就在（Observable 报告里的玩家实体被跳过），本版把它做**扎实、可见、可调**：

- **命名已用真实报告核对**：报告里玩家的 `type` 就是 `minecraft:player`（在 91 MB 的实测报告里找到 34 条），过滤确实命中；
  而**机器实测**这条路本来就不含玩家 —— mixin 只挂「原版机器方块实体 tick」「整合包原生机器回调」「收割机任务」，
  玩家实体不经过这些路径，所以玩家站在区块里不会给该区块加分。
- **可配置**：新增 `observableIgnoredEntities`（默认 `["minecraft:player"]`）。若还想把「玩家带来」的东西一起排除，
  可加 `minecraft:item`、`minecraft:experience_orb` 等；排除太多会掩盖真正的机器卡顿，所以默认只排玩家本身。
- **可见**：
  - 开服：`区块检测排除实体：minecraft:player（这类实体在 Observable 报告里不计入区块耗时，区块限制只盯机器…）`
  - 收到报告：`…（条目 6157 个，已排除 34 条玩家/忽略实体不计入区块卡顿）`
  - `/lagcontrol observable`：`…已排除 N 条不计入区块卡顿的实体（minecraft:player）`
- **测试**：4 项纯逻辑检查（玩家被排除、普通生物仍计入、空值不误判、`netmusic:music_player` 这种名字里带 player 的方块不会被误排）
  ＋ 玩家负载 GameTest 增加「排除计数」断言（50 ms/tick 的玩家开销被丢弃、纯玩家区块不受任何处罚、计数增加）。27 项测试全绿。

## 2.0.17：`freeze`/`release` 支持脚下区块（`~ ~`）＋ 商店涨价封顶 50%

### 一、冻结与解除支持「脚下区块」
- `/lagcontrol freeze`（不带参数）= 冻结**你脚下的区块**；`/lagcontrol freeze ~ ~` 完全等价（`~` 由 `ColumnPosArgument` 按执行者位置解析）。
- `/lagcontrol release` / `/lagcontrol release ~ ~` = 解除脚下区块。
- 也支持方块坐标：`/lagcontrol freeze ~-16 ~`、`/lagcontrol freeze 320 -64`（这两个是**方块**坐标，自动 `>>4` 换算成区块）。
- 原写法保留不变：`/lagcontrol freeze <维度> <区块X> <区块Z>`（这里仍是**区块**坐标）。
- 手动冻结写入永久冻结标记（`frozen=true`、全额没收、落盘），只有管理员能解除；执行后广播并回显解析出的区块与方块范围。
- 新增 `LagControl.freeze(Key)`（此前只有 `release`），并有 GameTest 覆盖「冻结 → 机器停止/全额没收 → 重复冻结无变化 → 解除 → 区块恢复无限制」全流程。

### 二、商店涨价封顶 50%，并修掉「重启累积涨价」
- 上限改为配置项：`config/ftlagcontrol.toml` 的 **`shopMaxPriceIncreasePercent`（默认 50）**，即买价最多涨到原价的 **1.5 倍**；填 `0` 即不涨价。

  现在原价写进存档（`data/ftlagcontrol.dat` 的 `shopBase`），**重启不再累积**；若整合包把某个价格改低，会自动按新价重新取原价。
- 新增命令：`/lagcontrol shopbase` 查看记录条数与当前上限；`/lagcontrol shopbase reset` 在整合包改价后重新取原价。
- 新增 6 项纯逻辑检查（封顶、取整、原价保存/读取往返）与 2 项 GameTest，测试 25 → **27 项**。

## 2.0.16：修复「出货箱一粒不卖」（新版脚本的箱主路径变了）

**故障现象**：出货箱不出货、玩家说「又不出货了」；服务端日志只有一条看似无害的
`[FT 卡顿定价] 出货箱脚本的结算条件行与已知版本不同，已保留整合包原样…`。

**原因**：出货箱脚本有两代结构——
| | 旧版（beta3，`34db8e8b`） | 新版（v1.5.2 系，`e7b69b28`） |
|---|---|---|
| `settlementData` | `block.getEntityData()`（有 `.data` 一层） | `entity.data`（**本身就是**数据对象） |
| 箱主取法 | `entityData?.data?.owner` | `settlementData.getString("owner")` |

2.0.15 及以前注入的守卫写死了旧路径：
`if (!FTLAG_PRICE_API.hasOwner(ftsbUuidString(settlementData?.data?.owner))) return;`
在新版脚本里 `settlementData?.data` 是 `undefined` → 箱主取到空字符串 → `hasOwner("") = false`
→ **在槽位扫描之前直接 return，整箱一粒都不卖**（`lastSettlementDay` 也不会推进，天天空转）。

**修复**：
- **删掉这个硬守卫**。箱主取不到时 `EconomyApi.unit` 会退回整合包原价、`record` 会跳过非法 UUID，
  本来就不需要提前中断结算 —— 出货优先，绝不阻断。
- **价格注入改用脚本自己的箱主表达式**：自动识别脚本里的 `let ownerUUID = <表达式>;`
  （旧版 `entityData?.data?.owner`、新版 `settlementData.getString("owner")`），价格乘区接到同一处。
- 开服日志新增一行，便于核对：`[FT 卡顿定价] 出货箱箱主表达式：settlementData.getString("owner")（已按脚本自身取法适配价格；结算不被阻断）`。
- 新增新版脚本夹具 `src/verification/resources/selling_bin_v2.js` 与 6 项纯逻辑检查：
  价格必须使用脚本自己的箱主表达式、结果里**不得再出现 `hasOwner`**、三条结算路径都要记账、
  新版「按箱主分时段结算」判断保持原样、桥接仍然幂等。

**顺带说明（不是故障）**：新版整合包把结算改成「每个箱主在清晨窗口 `0..1200` 内独占 200 tick 的一段」
（`ftsbOwnerBatchAllows`），所以一天里只有属于该箱主的那段时间会出货，其余时间箱子不会有动静。

## 2.0.15：`/lagcontrol window` 运行时改评估窗口

以前要验证「区块检测」是否在跑，得改 `config/ftlagcontrol.toml` 里的 `measurementWindowTicks` 再重启；现在一条命令即可，而且**立即生效并写回配置**：

但说明**验证完要调回 24000**（`/lagcontrol window 24000`），被误冻结的区块用
`/lagcontrol release <维度> <区块X> <区块Z>` 解除。

## 2.0.14：区块检测按原来那套跑，并且看得见（不依赖 Observable）

区块检测的实现**一直是同一套**（与最早的独立版 `qys-lag-economy.jar` 逐类一致），本版没有换实现，只是把它做成「看得见、可自证、且不依赖 Observable」：

- 检测链路：`MachineTickMixin`（原版机器方块实体 tick）＋`NativeSchedulerMixin`（整合包原生机器回调）＋`HarvesterMixin`（收割机任务）
  → `ProductionGuard` 计时并扣除子帧 → `LagControl.record` **按区块累计** → 每 24000 tick 统一评估算出 μs/tick → 限产／冻结。
  被识别的机器：`farmingtales` / `create*` / `farm_and_charm` / `ftlagcontrol` 命名空间，以及原版熔炉、高炉、烟熏炉。
- **Observable 只是可选叠加**：报告到达时按 `取更差的一份` 合并进同一次评估；没有报告时检测照常，`/lagcontrol` 会写「未使用 Observable」。
- 每次统一评估打一行：`区块检测（窗口 24000 tick）：机器实测 37 个区块（未使用 Observable）；当前 3 个受限区块`。
- 整窗口一个区块都没测到时（只提醒一次）：`本窗口没有任何机器实测数据：…（对照启动时的注入自检；被识别的命名空间=…）；这项检测与 Observable 无关，不会被它影响`。
- `/lagcontrol` 增加一行：`区块检测：本窗口已实测 N 个区块（机器实测，不依赖 Observable；Observable 叠加 K 个）…`。
- 新增回归测试 `realMachineTicksAreAttributedToTheirChunk`：在测试世界里放一台真熔炉，让它真的 tick，断言耗时被记到它所在的区块，
  且**全程没有任何 Observable 报告**（`Observable 叠加 = 0`）。测试 24 → **25 项**。

## 2.0.13：收到报告但「不采用」时也要吭声

2.0.12 的自检暴露了第二种「看起来失效」：报告来了、被本模组**主动跳过**，但日志里什么都不写。典型场景是**单机采样时开了暂停菜单/窗口失焦**——服务器刻几乎不推进，Observable 会给出 `Profiler ran for 41 ticks` 这种报告，本模组按「少于 100 tick 不采用」丢掉（这是对的：41 tick 的样本会把 μs/tick 放大几十倍，直接误冻结机器），但以前没有任何日志。

- 现在会打：`[FT 卡顿管控] 收到 Observable 报告但未采用：采样只有 41 tick（少于 100 tick 不采用）；单机开暂停菜单或窗口失焦时服务器刻几乎不推进，采样期间请保持游戏运行（专用服务器不受影响）`。

- 跳过的原因同样保留在 `/lagcontrol observable` 的状态行里。

另外记录一个与本模组无关、但会让人以为「Observable 失效」的上游问题：**Observable 官网上传接口 `POST https://observable.tas.sh/v1/add` 目前对所有请求返回 HTTP 500**（连空 body 都 500，11.8 MB 与 2.2 MB 的报告都一样），客户端只会提示「无法上传分析报告」，报告仍会存到本地 `observable_profiles\`，可在 https://observable.tas.sh/ 手动上传。

## 2.0.12：把「Observable 接入」做成能自证、且绝不拖累 Observable

围绕「Observable 失效」的排查与加固。管控规则、阈值、命令格式都不变。

- **绝不把异常抛回 Observable**：mixin 处理体整段包 `catch (Throwable)`。以前若本模组在 Observable 生成报告的方法里抛错，会把 Observable 自己的出报告流程打断（客户端拿不到结果，表现就是「Observable 失效了」）；现在最坏也只是本模组不生效，Observable 照常。
- **启动就写清「哪些钩子真的生效」**：本模组的 mixin 配置是 `defaultRequire: 0`（2.0.3 为了不让某个注入失败直接崩服），代价是**注入失败完全静默**。现在开服日志多两行：
  - `[FT 卡顿管控] 注入自检：11/11 已生效`（有问题时写 `未生效：ObservableMixin(未注入)`）
  - `[FT 卡顿管控] Observable 接入自检：报告接口可用（create(Map, Map, int, TraceMap)）`
- **收到报告就打一行**：`[FT 卡顿管控] 收到 Observable 报告：采样 1200 tick、区块 37 个（条目 512 个），已并入下一次统一评估`。
  有这一行 = Observable 数据确实进了本模组；没有 = 报告根本没生成到那一步。
- **新增 `/lagcontrol observable`**：
  - 不带参数：显示注入是否生效、已收到几份报告、最近一份的规模，或最近一次未采用的原因。
  - `/lagcontrol observable <秒数>`：用 **Observable 自己的 Profiler 实例**触发一次真实采样（等于替你按一次 Observable 采样）。采样结束最多等 15 秒：出现上面那行说明链路正常；一直没有，说明卡在 Observable 生成报告那一步（那一步本模组不参与，也不会拖慢它）。
- `/lagcontrol` 主输出多两行：Observable 接入状态 + 自检结论。
- **新增回归测试**：`everyMixinInjectionIsApplied` 断言 11 个注入全部生效（以前静默失效没人发现），Observable 的端到端测试也加了「注入已生效」断言。测试 23 → **24 项**。

## 2.0.11：查清并修掉「圈地团队扣减不生效」

本版是围绕「扣减怎么没生效」做的排查与加固，规则、阈值、命令都不变。

- **根因①：FTB 接口解析失败被永久记住（已修）**。
  旧代码第一次解析 FTB Chunks/Teams 反射入口时，只要那次失败（FTB 尚未加载完、调用时机过早、类名没对上），就会把「FTB 不可用」这个结论**永久缓存**，之后所有团队人均统计与扣减全部静默失效，重启前不会自愈。
  现在只有**真正解析成功**才缓存；失败不写缓存，下一次采样/结算自动重试。
  日志/命令里的表现：结算时打一次 `[圈地开销] 未检测到 FTB Chunks / FTB Teams，圈地团队卡顿分摊不生效（其余管控照常）`；`/lagcontrol teams` 直接回 `未检测到 FTB Chunks / FTB Teams，圈地团队扣减不生效`。看到这两条说明是接口没就绪，而不是「算出来是 0」。
- **根因②：认领区块和实测区块对不上时没有任何提示（已加诊断）**。
  扣减要靠「认领区块坐标 = 实测区块坐标」把 μs 算到团队头上；坐标维度错位、团队没圈到机器所在区块时，结果是**静默的 0**。
  现在每天结算会打印一行：
  `[圈地开销] 结算完成（第 N 天）：认领区块 A，当天实测区块 B，对上团队 C，扣减团队 D（人均按在线人数摊分）`
  并且当 B > 0 但 C = 0 时额外打 `WARN`：`当天有 B 个区块的实测数据，但都不在 FTB 认领区块内（认领 A 个）`，直接说明机器没建在圈地内，不用再猜。
- **`/lagcontrol teams` 增加排查信息**：标题行显示结算窗口范围与人均摊分方式；第二行显示**上次结算的状态**（第几天、认领/实测/对上/扣减计数）以及当前游戏刻、是否正处在结算窗口内；每行团队显示 `在线 a/b 人，合计、人均 μs/tick → 今日 -P%`。
- **真实 FTB 端到端回归测试（新增 `TeamLagGameTests`）**：在测试服务器里用**真的** FTB Teams/Chunks 建队、圈地、灌入 800 μs/tick 样本，断言：本队成员收入 ×0.5、非本队玩家 ×1.0、无人在线的团队当天不扣、结算结果能落盘。现在共 **23 项必需测试**全绿（含原有 31060 项纯逻辑检查）。

排查「扣减是 0」时的顺序：`/lagcontrol teams` → 看「当天实测区块」是否为 0（观察期未满 / 机器没在跑）→ 看「对上团队」是否为 0（圈地范围与机器区块对不上）→ 看在线人数（无人在线当天不扣，设计如此）→ 看 `teamPenaltyEnabled` 与结算窗口是否和出货箱窗口重叠。

## 2.0.10：继续压低机器热路径与 Observable 分析开销

- **机器 tick 合并判定**：冻结门禁、机器类型判断和限产快照合并为一次入口；每台机器每 tick 不再重复查询机器类型和区块限制。

- **Observable 后台分析减配**：报告/条目访问方法按类缓存，维度字符串每个维度只生成一次，区块耗时先用可变计数器聚合，避免大型报告中每条记录反复做方法查找和 `Double` 装箱。
- 管控规则、阈值、存档格式和命令保持不变。

## 2.0.8：圈地团队扣减与出货箱同一个结算窗口

## 2.0.7：圈地团队卡顿分摊（按人均 μs 每天扣团队收入）

新增第四个波动乘区：**圈地（FTB Chunks 认领区块）造成的卡顿按团队摊到人头上，每天扣团队内玩家的收入**。

计算方式：

1. 每 20 分钟的统一评估里，把每个区块的实测耗时（μs/tick）按天累计（当天所有窗口取平均）。
2. 每天（游戏日切换时）结算一次：把区块按 **FTB Chunks 认领归属**分组 → 得到团队当天合计 μs/tick。
3. **人均量 = 团队合计 ÷ 团队人数**（取 `FTB Teams` 成员数，含离线成员）。
4. 人均量映射为当日收入扣减：

| 团队人均 | 当日收入扣减 |
| --- | --- |
| < 200 μs/tick | 0（不扣） |
| 200 μs/tick | **10%** |
| 350 μs/tick | 20% |
| 500 μs/tick | 30% |
| 650 μs/tick | 40% |
| ≥ 800 μs/tick | **50%（上限，每天最多扣一半）** |

5. 扣减作为**独立乘区** `(1 − 扣减比例)` 参与结算：
   `单件结算价 = 原价 × 堆量行情 × 财富商品倍率 × 卡顿倍率 × 圈地团队倍率`，
   与另外几个波动系统一起相乘（在线入账与离线箱内金币两条路径都走同一入口）。

配置（`config/ftlagcontrol.toml`，重启生效）：

```toml
teamPenaltyEnabled = true          # 开关
teamPenaltyStartMicros = 200.0     # 人均达到该值开始扣
teamPenaltyMaxMicros = 800.0       # 人均达到该值扣到上限
teamPenaltyMinPercent = 10.0       # 起点扣减比例（%）
teamPenaltyMaxPercent = 50.0       # 上限扣减比例（%）
```

> 想让 200 μs 处从 0% 线性升到 50%，把 `teamPenaltyMinPercent` 改成 `0` 即可。

其他说明：

- 依赖 `FTB Chunks` + `FTB Teams`，全部走反射调用；**未安装时该乘区恒为 1**，只记录一次日志，其余功能不受影响。
- 结算结果写入世界存档（`data/ftlagcontrol.dat` 的 `teamPenalty` / `teamPenaltyDay`），重启后继续生效到下一天。
- 管理员查看：
  - `/lagcontrol` 增加 `圈地团队扣减=…（N 个团队，M 个在扣；最重「队名」人均 X μs/tick -Y%）`
  - `/lagcontrol teams` 列出扣减最重的前 10 个团队（队名、人数、合计/人均 μs/tick、扣减比例）
- 结算时会向该团队在线成员发送提示，并在服务端日志打印一行。

## 2.0.5：按 spark 报告优化服务器线程开销

对服务端 spark 采样报告（`https://spark.lucko.me/uZqeOJKcLc`，仅 Server thread，142 秒，TPS 7.6 / MSPT 120ms，15 人）
按模组自用时排序后，本模组（ftlagcontrol 2.0.3）是**可优化项里最大的一块**，逐项修掉：

| 热点（自用时间占比） | 原因 | 处理 |
| --- | --- | --- |
| `ReflectionAccess.field` → `Class.getDeclaredField` → `NoSuchFieldException`（≈2.5%~3%，其中异常构造 `fillInStackTrace` 1.68%）| 沿继承链用 `getDeclaredField` 找字段，找不到就抛异常；每个受限区块的机器每 tick 都要走一次 | 改为按「类+字段名」缓存已解析的 `Field`，遍历 `getDeclaredFields()` 不走异常路径；查不到缓存哨兵值，不重复扫描 |
| `ProductionGuard.itemCounts` / `finish` → `CombinedInvWrapper.getIndexForSlot`（3.62%）| Create 机器的组合库存每取一个槽位都要线性查找子库存，且每 tick 快照+没收各扫一遍 | 展开 `CombinedInvWrapper` 的子库存逐个读取，索引变 O(1)，保留 512 槽上限 |
| `ProductionGuard.working`（1.63% + 1.22%）| 每 tick 每台机器做一次注册表查询 + `ResourceLocation.toString()` 分配 | 结果只取决于方块，按方块缓存 |
| `MachineClock.refresh`（4.9ms 含子调用）| 每 tick 取区块键、查时钟重置表，而该表绝大多数时间是空的 | 表空直接返回，连键都不取 |
| `LagControl.frozen` / `loss` / `Key.at` | 每次调用都 `dimension().location().toString()` + 新建 Key 记录 | 缓存维度字符串与上一个「坐标→键」，并在这两张表为空时直接短路 |

总计约服务器线程 **7%~8%** 的开销被移除，同时显著减少异常对象与字符串的 GC 压力。
注：报告里其余大头（minecraft 33.5%、java 23.1%、JVM/原生 GC 屏障 21.3%、create 4.2%）属于整合包与 JVM 本身，
不在本模组范围内。

## 2.0.4：评估节奏改为每 20 分钟统一一次，阈值改为 1000 起限产 / 2000 冻结

- **统一评估**：机器实测与 Observable 报告不再各自随时改限制，改成每 `measurementWindowTicks`

- **冻结样本**：默认 `consecutiveSamplesBeforeFreeze = 1`，即某次 20 分钟评估达到 2000 就冻结；

- **配置迁移**：旧配置里存着旧默认值，首次开服会按 `configVersion` 自动改写为新值并写回（只执行一次）。
- **显示不受影响**：`/lagcontrol` 的 TPS/MSPT 与收入档位仍每 200 tick 刷新（10 秒），

- 测试同步更新：冻结线、限产曲线断言改为读配置值，Observable 用例改为「报告 + 手动触发一次统一评估」。

## 2.0.3：修复运行期崩服与升级容错

2.0.2 让服务器能启动了，但 2.0.3 修掉了启动之后才暴露的崩服与升级脆弱点：

- **运行期崩服（严重）**：`ProductionGuard.inventory()` 对机器的 `inventory` 字段用反射调用 `InventoryKJS.kjs$asContainer`，
  当该字段不是 KubeJS 库存类型时，`Method.invoke` 抛的是 `IllegalArgumentException`（**不是** `ReflectiveOperationException`，旧代码抓不住），
  异常一路冒泡到区块 tick：`object is not an instance of declaring class`，服务器当场崩。
  触发条件是「区块被黄色限产后，该区块里的机器开始 tick」——所以是限产一生效就崩。
  现在先 `isInstance` 判断再调用，并捕获 `RuntimeException`；`begin/end/callback/confiscateArm` 也全部兜底：
  **管控自身出错只跳过这一台机器，绝不再崩服**，并留下按机器类去重的错误日志。
- `ReflectionAccess`：找不到方块实体字段时返回 `null`（原来是抛 `IllegalArgumentException`），同属崩服隐患。
- `ftlagcontrol.mixins.json` 改为 `defaultRequire: 0`：升级整合包后某个挂钩的目标方法被挪走时，
  只少一个挂钩并留下 Mixin 警告，不会再把服务器卡在启动阶段（1.0.0/2.0.1 的启动崩溃正是这么来的）。
  挂钩是否仍然生效由 `gradle runGameTestServer` 在真实魔法木桶上验证。
- 出货箱“结算条件行”改为**可选挂钩**：新整合包若改写了这一行，价格倍率、箱主校验、收入账本照常适配，
  只在 `/lagcontrol` 显示“结算条件行未识别，零价商品可能仍留在箱内”。
- 回归测试：GameTest 新增“机器 inventory 字段为外来对象”用例（旧版必崩）；规则检查新增“结算条件行未知仍能完成适配”。

## 2.0.2：修复升级整合包后服务器无法启动

2.0.1 在魔法木桶 1.0.15-kubejs 及更新版本上会**直接导致服务器无法启动**，本版修掉两处：

- **原生调度挂钩注入失败（致命）**：2.0.1 的 `NativeSchedulerMixin` 写死 `require = 2` 并挂 `beforeCollection` + `tickLevel`；木桶 1.0.15 起把结算循环抽成私有方法 `drain(...)`，`tickLevel` 里不再调用回调，注入变成 1/2，Mixin 抛 `InjectionError`，KubeJS 记成启动脚本错误，服务器停在 `COMPLETE` 阶段。现在改为两个挂钩分别覆盖 `beforeCollection` 与 `tickLevel`/`drain`，并且 `require = 0`：某个调用点在某版木桶里不存在时只跳过该处，**永不中断启动**。已在木桶 1.0.11 与 1.0.15 上分别跑通 22 项 GameTest，导出转换后字节码确认 `beforeCollection`+`tickLevel`（1.0.11）与 `beforeCollection`+`drain`（1.0.15）两条回调路径都挂上了管控。
- **脚本适配不再抛异常**：出货箱 / 树液脚本结构不匹配时，旧版抛 `IllegalStateException`，同样被 KubeJS 当成启动脚本错误。现在改为记录错误日志 + 在 `/lagcontrol` 状态里显示“未安装：脚本结构不匹配，已退回整合包原始定价/产出”，脚本原样返回，服务器照常启动；此时出货箱按整合包原价结算，区块限产 / 冻结与财富波动不受影响。
- 锚点匹配改为容错：`let`/`const`/`var`、空白差异、结算条件行新增的额外条件都能识别，并且只去掉“总价大于 0”那一个条件。对已知的出货箱脚本（1.5.2_beta3 与 v1.5.2 两份），2.0.2 生成的适配结果与 2.0.1 **逐字节一致**。
- 验证：32540 项规则检查 + 22 项 GameTest 全部通过；启动日志里出现“出货箱桥接=/树液桥接=”状态，升级整合包后先看这两项与 KubeJS 启动日志。

区块处罚读取 Observable 报告时排除玩家实体的实际计时，不采用“在线人数 × 固定耗时”的估算。
玩家带来的区块加载、网络处理等间接负载尚未完整归因扣除，因此当前保持全局降价关闭；状态中的 TPS/MSPT 仍是全服原始指标。

## 收入：三个独立乘区

单件结算价 = 整合包原始单价 × 原有堆量行情倍率 × 财富商品倍率 × 卡顿倍率。

单件结果小于 1 时直接记为 0，再乘数量。64 件单价 0.5 的商品也只结算 0，不能凑整规避。
单件结果大于等于 1 时保留小数，沿用原出货箱对总金额四舍五入，避免无关的逐件向下取整损失。
零价商品仍被正常售出、扣除并计入市场销量；在线所有者收到零收入提醒；同日不会重复结算。
没有有效所有者的出货箱暂停结算并保留商品，先按整合包原有方式绑定箱主，防止使用无主箱绕过财富分档。
不扣已有存款，不追缴既有库存。

**以下全服卡顿档位仅在管理员显式设置 `enabled=true` 且 `enableGlobalLagIncomeReduction=true` 后启用；当前默认不执行。**
启用后的卡顿评级取 `min(实际 TPS, 1000 / 实际 MSPT)`，每 200 tick（10 秒）刷新一次显示与档位；恶化立即进入下一档，恢复要连续 3 个窗口。此评级尚未扣除玩家间接负载，不建议在完成归因前开启。它只影响收入乘区，不改变区块限产/冻结的 20 分钟评估节奏。
关闭全局开关后立即按卡顿倍率 ×1 结算并对外显示0档，不等待三个恢复窗口，也不会沿用此前残留的降价档位。

| 有效 TPS | 最高财富档卡顿倍率 |
| --- | --- |
| 大于 15 | ×1.00 |
| 12 < TPS ≤ 15 | ×0.70 |
| 10 < TPS ≤ 12 | ×0.40 |
| TPS ≤ 10 | ×0.10 |

其他财富档按 `1 - 本档降幅 × 财富比例` 缩放，最贫档不受这一乘区影响。×0.10 是**卡顿乘区下限**，不是三个乘区相乘后的收入保底。

参考提供的 qys-progressive-taxation 1.0.0：

- 财富门槛：0 / 1万 / 10万 / 100万 / 1000万 / 1亿，对应财富比例 0 / 0.2 / 0.4 / 0.6 / 0.8 / 1。
- 财富依据取累计销售收入与 SDM 当前余额的较大值；在线读取 SDM API，离线读取 SDM 已载入的服务器余额表，并缓存自己的销售账本。
- 旧累计收入兼容 `ftEconTotal`、`ft_econ_total`、`ftEconIncome`、`fteconTotal`；离线玩家首次结算可从玩家存档读取这些字段。
- 商品原价分档 ≤10 / ≤30 / ≤80 / 高价，因子分别 0.30 / 0.65 / 0.80 / 1.30。
- 商品倍率为 `1 + (商品因子 - 1) × 财富比例`；低价商品沿用高财富档额外压价和 ×0.30 保底。
- 若存在有效 `config/ftecon-config.json`，读取其中的财富与商品分档；缺失则生成默认配置。旧兼容 API 也取消不足1强制保底为1，不重复追加旧税。
- 堆量行情沿用现有出货箱的 `(100 - discount + boost) / 100`；不擅自打开或重置整合包的市场开关和销量。
- 卡顿收入倍率接管本整合包出货箱的金币入账、离线箱内金币、主动箱内金币三条路径；不扣任务奖励或玩家转账。SDM 商店购买价格仍走财富模组原来的涨价规则，不套卡顿降价。

例如最富档，原价 1000、堆量降价 60%、高价商品因子 1.3：当前即使 TPS ≤10，单件收入也是 `1000 × 0.4 × 1.3 × 1 = 520`。只有显式重新开启全服卡顿降价且进入最低档时才变为52。

## 区块产出限制与冻结

以**单个区块平均每服务器 tick 的耗时**为依据，不是全服 MSPT，更不是将 ns 误当 μs。
本地采样只统计受管控的机器工作；Observable 报告聚合排除 `minecraft:player` 实体记录，其他实体及方块实体仍正常计入。
例如同一区块中玩家实体50 ms/tick、其他实体1 ms/tick，处罚只按后者的1000 μs/tick判断；只有玩家的区块不会因该报告新增处罚。已有红色冻结不会因本次升级自动解除，仍须管理员确认后解冻。

| 区块耗时 | 默认行为 |
| --- | --- |
| <1000 μs/tick | 不限制 |
| 1000 μs/tick | 黄色边界，随机没收约 25% 新产出 |
| 1250 μs/tick | 黄色边界，约 39% |
| 1500 μs/tick | 黄色边界，约 53% |
| 1750 μs/tick | 黄色边界，约 68% |
| ≥2000 μs/tick，达到即冻结（默认连续 1 次评估） | 红色边界，冻结机器工作 |

区间内线性变化，按每批产出做随机舍入，单个产物也有概率被没收。大量物品/流体不逐单位循环抽签。
冻结阈值可上调，代码硬下限为 1000。限产起点、100% 没收线与冻结线都在 `config/ftlagcontrol.toml` 里，改完重启生效。

- 自动计时固定机器的真实 tick、农场物语 NativeMachineScheduler 回调和魔法木桶收割任务，弥补 Observable 看不到整合包日常生产调度的部分。
- 安装 Observable 时自动接收每次完成的原始报告，合并实体和方块实体到对应维度区块。`rate(ns) × entryTicks / profileTicks / 1000` 换算为 μs/tick。少于100 tick的报告不用于处罚。
- Observable 分析在后台进行，处罚返回服务器主线程；不会自动开启 Observable 性能采样，也不需要上传报告或安装之前的报告器。可与独立 Observable 报告器并存。
- 外部报告的黄色限制保留到下一次统一评估，没有新的高耗时证据就会解除；持续冻结不受这个期限影响。相同报告对象不会重复计为两次冻结证据。
- 每次首次限产、升级冻结或管理员解除，向全服广播维度、区块 X/Z 和实际方块坐标范围。
- 黄色限制可以随新采样恢复；**红色冻结写入世界存档，即使 TPS 恢复、区块卸载、服务器重启也不会自动解除**。

## 产出保护与兼容范围

- 农场物语树液采集器、鱼塘、蟹笼及其原生生产回调；Create 固定方块实体机器；原版熔炉/高炉/烟熏炉。
- 作物的玩家破坏和自动收割掉落；跨区块收割也检查作物所在区块，不能用隔壁的正常机器绕过。
- 物品处理检查加工前后的新增量，保留已有输入、燃料及旧库存；不会扫描删除玩家背包、普通箱子、物品仓库或储液罐。
- 流体处理检查新的流体增量；Create 搅拌盆另在配方输出阶段拦截物品和流体，模拟容量检查不扣产物，隔壁搅拌器不能加工冻结的盆。
- Create 机械臂在每次实际取到新物品后处理新增持有量，不会每 tick 重复扣除；机械手/传送带加工另拦截配方结果，冻结的加工器也不能被相邻传送带调用。
- 树液采集器在产出建立时处理没收。整批被没收后重新开始完整生产周期，堵住“成熟状态不断补发产物”的问题。
- 冻结时禁止右键操作受管控生产机器，防止交互路径继续触发加工；不禁用普通存储箱。
- 管理员解除后，已知日历型机器重置生产日计时，防止鱼塘/蟹笼/树液采集器将冻结期间积累成追补产出。旧库存不清空。
- 针对普通 Forge 能力库存最多检查512槽、32个流体槽，防止管控功能本身产生无界开销。

范围说明：这是生产机器管控，不是暂停整个区块的世界模拟；玩家、生物、普通容器和流体方块自然流动不会被冻结。
移动装配体（列车、轴承上的移动机械）及第三方模组私有/异步产出接口不在这一版固定工作方块适配范围，不能据此宣称所有附属模组都已覆盖。

## 管理员命令

需要 OP 等级2，或从控制台执行：

```text
/ftprice
/ft wealth status
/ft wealth true
/ft wealth false
/lagcontrol
/lagcontrol list
/lagcontrol release minecraft:overworld -1 -2
/lagcontrol release minecraft:the_nether 12 34
```

`/ftprice` 是普通玩家可用的自身价格查询，其余设置和解除命令需要管理员权限。
`/ftprice` 明确显示全局降价开关和停用时的 ×1；`/lagcontrol` 分开显示全服原始 TPS/MSPT、全局收入降价开关、降价档位及区块管控开关，并提示已排除 Observable 玩家实体计时。

参数是**区块坐标**，不是方块坐标；方块坐标除以16并向负无穷取整。`-1,-2` 区块对应方块 X=-16..-1、Z=-32..-17。
解除同时清除该区块限制与处罚计数，并给予默认600秒保护期。保护期后仍严重卡顿可以再次触发，须真正减少机器负载。
`/lagcontrol list` 最多列50条。冻结存档位于世界的 `data/ftlagcontrol.dat`。

配置：`config/ftlagcontrol.toml`，包括限产起点、100%没收线、冻结线、统一评估间隔、冻结连续样本数、解除保护期和边界粒子开关。
当前推荐设置如下，旧配置没有全局开关时也默认关闭。停服修改后重启生效：

```toml
enabled = true
enableGlobalLagIncomeReduction = false
reductionStartsMicrosPerTick = 1000.0     # 1000 μs/tick 开始限产
fullConfiscationMicrosPerTick = 2000.0    # 2000 μs/tick 全额没收
freezeMicrosPerTick = 2000.0              # 2000 μs/tick 冻结（硬下限 1000）
measurementWindowTicks = 24000            # 24000 tick = 20 分钟统一评估一次（上限 24000）
consecutiveSamplesBeforeFreeze = 1        # 达到冻结线即冻结；改 2 表示连续两次评估（约 40 分钟）
```

`configVersion` 由模组自己维护：从 2.0.3 及更早升级上来时，会在首次开服自动把
限产起点/全额没收线/冻结线/评估窗口/冻结样本数改写成上面的新值并写回配置文件
（旧版本默认值是 500/2000/2500/200/2，不迁移的话服务端会继续按旧值跑）。
迁移只在 `configVersion` 落后时执行一次，之后你在配置里的手动修改不会被覆盖。

`enabled=false` 停止卡顿收入乘区、黄色处罚与新的自动冻结，不关闭财富商品波动，也不会隐式解冻已经封锁的区块，既有红色冻结仍须管理员解除。

## 安装与验证

退出游戏/停止服务器后将成品放进服务端 mods，再重启。不要热替换。
只安装合并版，移走两个旧 jar；保留原税收/行情配置与原脚本文件。出货箱、树液脚本只在 KubeJS 加载时做内存适配，不改磁盘上的整合包脚本。
对当前脚本的关键结构做严格检查，遇到不兼容版本会明确报错而不是默默使用错误价格。升级整合包后先检查 `/lagcontrol` 的桥接状态和 KubeJS 启动日志。

构建使用 Java17 / Gradle8.8。`gradle build runGameTestServer` 包括纯规则检查和加载真实 Observable、Create、KubeJS、农场物语、SDM 商店与 SDM 经济的专用服务器测试。
2.0.1 通过32534项纯规则检查和22项 GameTest，新增验证默认关闭与旧档位失效、全局开关不影响区块限产/冻结，以及真实 Observable 报告中的玩家实体排除。
测试在独立临时世界执行，使用当前整合包出货箱/树液脚本的只读快照；不打开用户存档。
成品不包含测试、脚本快照或依赖 jar。部署工具比对源文件 SHA256、成功构建日志和实际模组测试结果，并拒绝在 Minecraft 运行时替换。
迁移备份目录中的 `migration.json` 记录原路径、SHA256和备份位置。回滚须先移出合并版，再按清单恢复旧 jar；不要恢复为旧版与合并版同时存在。
