# SDMShop 服务端安全补丁与审计 1.1.0

独立的 Minecraft 1.20.1 Forge 服务端 MOD，在原有修改、购买和出售审计中加入提权漏洞阻断。拒绝未授权编辑、未批准的指令商品和不安全交易；不自动封禁、不恢复历史商店、不依赖或修改 FTBoss。客户端不需要安装。

## 安装

1. 停止服务器，备份商店配置和存档。
2. 如果装过审计 1.0.0，先从服务端 `mods` 移出旧审计 JAR；同一 MOD ID 只能留一个版本。将 `sdmshop-server-audit-forge-1.20.1-1.1.0.jar` 放入**服务端**的 `mods` 文件夹，再启动服务器。保留原有 SDMShop 与其前置，不用替换商店 JAR。
3. 在控制台或 OP 账号执行 `/sdmaudit status`。正常应显示“安全补丁已启用”和日志目录，文件错误、钩子错误应为 0。启动日志中应有 `SDMShop security patch active`、`SDMShop audit active`；本版集成测试应用了 17 个目标类钩子。
4. `/sdmaudit snapshot` 手动记录当前商店取证快照，不会修改或恢复任何商品。

适用：Forge 1.20.1、SDMShop Rework `1.20.1-6.11-pre`。集成测试使用 Forge 47.4.10，以及本地 `[SDM商店修复版]sdmshoprework-forge-1.20.1-6.11-pre-max1024-fixed-ft-editor1.jar`、Architectury 9.2.14、FTB Library 2001.2.12、SDM Economy 1.7.2、SDM UI Lib 1.8.3。依赖由原商店提供；审计 JAR 不内嵌这些 MOD。不要把此 Forge JAR 用于 NeoForge、其他 Minecraft 版本或不同 SDMShop API。

## 提权修复（优先项）

原问题不是已证实的隐藏后门，而是可被利用的权限校验缺失：普通玩家能发编辑包改商品，再利用 `elevatePerms` 指令商品以二级命令权限执行任意新增指令。二级命令权限不等于原版 `/op` 所需的四级权限，但仍可以执行许多危险指令或第三方管理命令。

- **编辑必须有服务端真实 OP≥2**：9 种编辑消息在读取并应用修改负载之前统一鉴权。客户端 GUI、客户端 OP 显示、`edit_mode=true` 或伪造编辑模式均不能代替服务端权限。OP≥2 的合法编辑保留；单独持有编辑模式的普通玩家会被拒绝。
- **指令商品必须在可信名单**：不从服务器当前商品自动学习。内置批准 fix2 原版的 11 条 Curios 扩展槽位指令；新增或已污染的指令商品默认拒绝。比较完整指令模板、`elevatePerms`、`silent`，任一变化都需要重新明确批准。此规则对 OP 购买也生效。
- **拦截直接调用**：不仅拦截购买消息，还保护指令商品自身的 `buy` 执行入口，防止其他调用绕开包级检查。批准的商品仍按原设计使用二级权限，不额外授予四级权限。
- **修复玩家占位符串号**：`{player}` 只替换在本次执行的局部字符串中，不再把商品指令永久改成首个购买者的名字。含此占位符的商品还要求玩家名为标准的 1～16 位英文字母/数字/下划线，拒绝选择器或参数注入。命令返回无成功结果时不扣款，记失败并回退本次限购计数。
- **安全与日志独立**：记录失败或审计服务不可用不会关闭鉴权。安全基准/可信名单加载失败则拒绝编辑和交易（fail closed），而不是悄悄退回不安全原行为。

自定义指令必须由**服务端控制台或 OP≥4**明确批准，不能通过普通商店编辑界面自动批准：

```text
/sdmaudit trust-command <分页UUID> <条目UUID>
/sdmaudit revoke-command <批准时返回的指纹>
```

批准前先核对商品的完整指令、权限标志、静默标志以及被调用命令的安全性。批准不会消除指令本身的危险性；不要批准陌生玩家提交的指令。名单保存在服务端 `config/sdmshop-audit-trusted-commands.json`，客户端无法通过本补丁的网络入口写入。批准按指令定义生效，不按条目 UUID 生效：相同指令定义的多个条目共享批准，撤销影响这些副本；价格、图标、条目位置不属于权限指纹。内置 11 条原版指令不在自定义撤销列表中。

## 交易防护

- BUY 和 SELL 都要求购买批数 `1..1024`；检查负价格、非正物品数量、乘法溢出、物品货币的 long→int 截断以及出售后余额溢出。
- 在购买包入口、实际执行前，以及原版物品/指令类型执行入口重新校验，覆盖 KubeJS 改价之后的校验。金币/物品货币付款入口也拒绝负数、不足余额或溢出金额。
- 按服务端数据检查分页和商品的限购：`已用+本次批数≤限额`，同时保护个人和全服共享限购。失败/中断且未形成完成并接受付款的交易，回退原处理器提前增加的分页/条目计数，并保存、同步；回退失败会阻止后续交易并报错，需管理员排查后重启。
- 修复限购存档遗漏：只有限购分页、没有限购条目的玩家数据也会保存；全服共享计数和个人计数分开持久化，不把用于客户端同步的合并结果误当服务端原始数据。兼容原保存格式的读取，但无法补回旧版已经遗漏的数据。
- 服务端重新检查分页和商品条件，使用当前购买者而不是客户端玩家：FTB Quests 要求列表内所有任务已完成；GameStages 检查所有非空阶段；MNA 检查启用的等级/阶级范围及阵营列表（允许任一匹配阵营）。未知条件、任务不存在、能力缺失或相关 API 无法检查时拒绝，不默认为放行。

此补丁不为任意第三方商品类型、KubeJS 脚本或命令提供事务回滚。命令已经产生的外部效果不能撤销；命令自身异常/部分执行或付款失败后必须人工核对。限购回退仅回退本次计数，不回滚全世界状态或外部 MOD 的效果。

普通物品仍遵循原需求：**成功买入非原商品时告警，不按物品基准自动禁购**。指令名单是另一层独立的执行授权；批准自定义指令也不会把它加入原版商品基准，所以成功购买仍可能产生非原商品告警。

## 固定原版商店基准

“原版”指用户指定的 fix2 整合包商店，不是仅允许 Minecraft 原生物品：

`C:\Users\YOUR_USERNAME\AppData\Roaming\.minecraft\versions\FarmingTales_ForgeⅡ v1.5.2fix2\config\SDMShop\sdmshop.snbt`

- 基准 SHA-256：`e4f5e1d25d41282b8868f1fab8757452e49c83677d25dbe260a6edc8b9490739`。
- 27 个分页，1050 个购买条目，1005 种去重后的商品身份，865 种物品注册 ID。
- 只把可购买条目的真实商品作为基准。出售条目、分页图标、商品图标不加入白名单。例如作为图标的 `minecraft:barrier` 不因此获得购买许可。
- 基准原文内嵌在审计 JAR 中，不从服务器启动时的现状自动学习，避免把已被玩家改过的商店误认为正常基准。安装后不依赖桌面路径，也不改写原配置。
- 普通物品比较注册 ID 与完整商品 NBT，保留 NBT 类型；同 ID 的额外附魔、属性、改名或其他 NBT 变体也可能不在基准内。忽略堆叠 `Count`，忽略价格、购买数量、分页、条目 UUID；空 `tag` 与空 `ForgeCaps` 视为缺省。
- 指令等非普通物品商品比较商品类型与完整 `entryType` 数据，不会把图标当作实际发放物品。
- 基准内已有的合法 NBT 变体允许购买。调整合法商品价格不会触发“非原商店物品”警告，但修改操作仍记录在修改日志中。
- 管理员故意增加新的商品/NBT 变体后，仍会被固定基准告警；需要审查新基准并重新构建，不会自动放行。

交付目录附有 `原版物品ID清单.txt`、`原版购买商品明细.json` 和 `原版商店摘要.json`，分别用于查看物品 ID、逐分页的商品类型/NBT/原价/数量、基准统计。ID 清单仅便于查看，不代替 JAR 内的 ID+NBT 校验。

## 非原商品购入警告

只有 BUY 请求经过原商店的购买执行方法、方法正常返回、且捕获到所有付款回调均接受时，才记 `SUCCESS`。随后检查购买前的商品定义；不在固定基准中的成功购入，每个请求写一条 `non_original_purchase_warning`。

警告同时写入服务器 WARN 日志、独立 `*-warnings.jsonl` 和每日人类可读日志。记录玩家名、UUID、OP/编辑模式、时间、维度/坐标、分页/条目 UUID、商品类型与 ID、购买批数/物品数量、价格、付款结果及余额变化、商品 NBT、基准哈希和原因。

例：

```text
[非原商店物品购入警告] 玩家=Example UUID="..." 商品=minecraft:dirt 数量=1 原因="ITEM_NOT_IN_OFFICIAL_SHOP" request=...
```

原因：

- `ITEM_NOT_IN_OFFICIAL_SHOP`：此物品 ID 不是 fix2 原商店的购买商品。
- `UNAPPROVED_ITEM_NBT`：ID 是原商店物品，但当前商品 NBT 不是任何原版允许的变体。
- `PRODUCT_TYPE_OR_PAYLOAD_NOT_IN_OFFICIAL_SHOP`：其他商品类型或其数据不在基准中。

余额不足、物品货币不足、无效数量、条件/限购拒绝以及出售都不会触发成功购入警告。它们仍写交易请求和结果。没有付款回调、付款拒绝、执行报错或执行中断分别使用未验证/拒绝/错误/中断状态，不冒充成功。

`SUCCESS` 依据 SDMShop 的执行完成与付款接受，不能替代对所有自定义指令/外部 MOD 最终效果的逐项验证。警告说明“此玩家买到了基准外的商品”，不单凭此判断该玩家就是修改者；应结合对应的修改记录追查。

## 独立日志

所有路径相对于**服务端根目录**，按配置时区的日期分文件；默认 `Asia/Shanghai`：

```text
logs/sdmshop-audit/
  YYYY-MM-DD-edits.jsonl          编辑请求、结果、变化和快照索引
  YYYY-MM-DD-transactions.jsonl   购买/出售请求、结果和付款信息
  YYYY-MM-DD-warnings.jsonl       安全拦截及成功购入非原商品的 WARN 记录
  YYYY-MM-DD-system.jsonl         启停、钩子/基准摘要、指令批准和撤销
  YYYY-MM-DD.log                  中文摘要，便于直接阅读
  snapshots/<SHA256>.snbt.gz      完整商店、编辑负载、交易商品前后的压缩取证快照
```

JSONL 每行是一个独立 JSON 对象，使用 `session`、`sequence` 和 `requestId` 关联同一服务器会话及请求。人类可读摘要转义换行、制表符和 ESC，避免玩家输入伪造日志行。中文文件为 UTF-8。

修改记录覆盖 9 种客户端编辑消息：创建分页/条目、整体商店变更、分页变更、分页条目批量变更、编辑分页/条目、移动分页/条目。合法编辑记录玩家、权限/编辑模式、前后哈希及字段变化。未授权编辑在执行原处理器之前写 `security_block`，不处理其整份负载，也不伪造成功的修改前后记录。

被拦截的交易写 `BLOCKED_SECURITY` 和 `blockedReason`；WARN 同时记录玩家名/UUID、操作、分页/条目 ID、数量和原因，并尽可能与交易 `requestId` 关联。典型原因：`EDIT_REQUIRES_SERVER_OP_LEVEL_2`、`UNTRUSTED_COMMAND_PRODUCT`、`INVALID_BATCH_COUNT`、`PRICE_OVERFLOW`、`LIMIT_EXCEEDED`、`SECURITY_NOT_READY`。第三方 API 不可用会出现 `SECURITY_CHECK_FAILED`，请查看相应依赖和商品条件，不要将它改成绕过鉴权。

定期扫描和商店保存后观察内存中的商店状态，补录其他途径的变化。无法关联玩家的变化标记 `UNKNOWN`，不猜测责任人。直接改磁盘但未加载进内存的配置变更不属于该扫描的检测范围。

快照按内容哈希去重；摘要限制差异数量和大字段长度，开启快照时完整数据保留在压缩文件。交易中的 `entryBeforeHash`、`entryAfterHash` 指向完整商品定义快照，可以查看未被摘要截断的 NBT。快照保存失败时仍尝试写操作记录，并在 JSON 中标记 `snapshotErrors`，同时控制台报错。磁盘/目录完全不可写时无法保证持久化，请监控状态命令中的文件错误。不要关闭快照后仍期望拥有完整大字段的历史版本。

写入使用有界单线程队列，满队列由调用线程写入，不静默丢弃；极端洪泛/慢磁盘可能拖慢服务器。正常停止等待写入队列，强制结束进程或掉电仍可能丢失尚未落盘的数据。日志和快照不自动删除，请留出磁盘空间并按需备份、归档。

## 配置

首次启动生成 `config/sdmshop-audit.toml`；修改后建议重启：

```toml
scanIntervalTicks = 200
maxInlineChanges = 200
saveSnapshots = true
timeZone = "Asia/Shanghai"
```

扫描默认每 200 tick（服务器正常 20 TPS 时约 10 秒）；直接编辑消息不是等到下一次扫描才记录。时区必须是有效的 Java 时区名称。

本版在记录工具中加入权限修复，但只能记录安装并成功启动之后的行为，不能补出此前没有记录的购买。它不自动清除既有污染商品、不恢复余额、不撤销旧 OP/权限，也不阻止持有操作系统文件权限、其他漏洞或其他恶意 MOD 的攻击者改文件。安装后必须人工审查现有商店、`ops.json`、权限系统与重要存档，备份仍然必要。

## 构建与测试

使用 Java 17 或 21、Gradle 8.8、ForgeGradle 6.0.54。主代码以 Java 17 字节码发布；主构建不需要私有 SDMShop 编译依赖。

```text
gradle --offline build
gradle --offline -PauditSmoke runGameTestServer
```

离线构建要求 Gradle/Forge 依赖已缓存。烟雾集成测试需要将原 MOD 复制到 `compat-libs` 并命名为 `sdmshoprework-6.11-pre.jar`、`architectury-9.2.14.jar`、`ftb-library-2001.2.12.jar`、`sdm-economy-1.7.2.jar`、`sdm-ui-lib-1.8.3.jar`。这些依赖不在发布 JAR 中。测试仅在 `run-audit-gametest` 的独立服务器运行，不使用真实存档；测试 MOD 也不进入发布 JAR。

`verifyAudit` 检查差异、64 位价格、交易状态、并发无丢行、UTF-8/日志注入、快照往返和失败保留记录，另含数量/价格/余额/限额边界、严格指令指纹、名单持久化和撤销、损坏文件拒绝；本版共 52 项纯代码断言。GameTest 调用真实消息和付款代码，保留原审计用例，并检查伪造编辑模式下的 9 种编辑拒绝、直接指令调用阻断、四级批准/二级拒绝、模板不变与不同买家、撤销、负数出售、溢出、个人/全服限购、失败时两类限额回退、不可检查条件拒绝、安全初始化失败拒绝，以及审计停止时仍保持安全拦截。

条件失败用例使用仅属于测试 MOD 的任务条件夹具，验证服务端无法检查时拒绝；实际 FTB Quests 完成状态以及 GameStages/MNA 的玩家能力状态，未在此精简测试环境中逐项完成真实 MOD 的成功/失败集成验收。相关桥接 API 按提供版本静态核对，若运行时不同则拒绝并告警，请先在完整服务器副本验证合法条件商品。

发布实包测试：先构建，将生成的 JAR 复制到 `compat-libs`，再运行 `gradle --offline -PauditSmoke -PauditJarSmoke runGameTestServer`。这一步加载发布 JAR 而不是主代码输出目录，检查 manifest 自动加载 Mixin、真实交易记录与商品快照；开发环境由 ForgeGradle 对发布包做映射转换。它不等于在用户完整服务端整合包中完成稳定性验证。
