# 新房间接入 FT 地牢

适用 FT 地牢怪物 0.17.0、Minecraft Java 1.20.1、Forge 47.4.10、Java 17。

## 在游戏中进入

保留既有入口门与火盆操作。**成功传送进 `ftdungeonmobs:dungeon` 后**，运行一次安全扩建检查；不会在安装模组、服务器启动或每 tick 扫描时改写世界。扩建失败不取消已成功的入场，也不改个人返回记录或入场窗口。

- 沿原大厅向南（+Z）走，阶梯通往 **31 号主场景**。
- 在连接路口向东（+X）走，再向南进入 **30_1 紫晶侧区**。
- 继续沿东支路到 X=80 的发光地板主干，通往九间 image2.5 参考设计的原版方块房间；不是只打包图片或 NBT。
- 已生成后不会每轮重建；玩家后来挖掘或改造会被保留。
- 管理命令需要权限等级 2，可在任意维度执行，实际施工只发生在 FT 地牢：

```mcfunction
/ftdungeon rooms status
/ftdungeon rooms build
```

没有强制覆盖、重置标记或自动修复命令。误放的结构、已建的旧建筑与生成后的人工作品不会被此接口自动清理。

原大厅最南端 Z=15，新增方块全部从 Z=16 开始。连接路仅允许复用 Y=63 的相同原地面方块；其余预留空间必须为空气且无液体、无实体。检查覆盖整个声明体积，包括模板未记录的坐标，而不只是模板内的实心方块。

模板不旋转、不镜像、不移动内部方块，原生已知形状放置同时关闭逐格的间接邻居形状重算，避免放置顺序使藤蔓等连接状态提前丢失；后续正常世界更新不被冻结。外置道路、阶梯、路灯、地基和苔石砖挡水边界不覆盖任何原始方块记录；30_1 首行 Z=0 本身没有记录，在该留白行增加入口落脚地板。两份模板底部 Y=64 另铺苔藓地基，承托选区底层的根须、蕨类与其它植物，不替换既有 Y=63 地面。

从大厅南口沿 Z=23 向东，X=62 的阶梯将原地面抬至 Y=64，X=79..81 为三格宽南北主干；每行从 X=80 向东分支，再各自向南接房间北入口。入口相对高度由元数据决定，最后几格有对应三格宽阶梯及落脚台。道路保留三格净高，海晶灯嵌入地板，不占行走空间。新增房间和道路不穿过 31 / 30_1，也不依赖原两间施工成功；各房仍须安全空间。

每间单独验证来源 SHA-256、DataVersion 3465、原版注册表和全部状态属性、禁用方块/实体/战利品、北侧 3×3 开口与完整地板、入口到内部安全点的干燥可步行连通。原生放置后逐格复核记录，并检查灯、植物等 `BlockState.canSurvive`，失败回滚且不写生成标记。真实液体不得暴露在模板边缘，主路不得穿过火、熔岩、深水、粉雪或蛛网。

完整房间体积再加一格边缘留白必须是无液体空气，包括未记录的稀疏坐标。道路可复用与计划完全相同的方块，但不同方块、占用净高、边界外坐标或路上/房内实体都会拒绝该间；不会清空玩家作品。共用路径的方块状态由世界坐标确定，先后生成不同房间不会互相冲突。每次只回滚本次施工，不回退已生成其它房间。

独立标记使用同一 SavedData 的 `Rooms` 列表，保存每间 `Id` 和 `Fingerprint`。指纹覆盖 ID、槽位、尺寸、入口、安全点、模板 SHA 与布局版本。后续新增房间只新增标记，不移动或重建旧房；已有 ID 的模板/坐标变更会报告 `changed` 并拒绝覆盖，不自动迁移玩家改建。只执行 `status` 不施工。某间缺失或不合格会逐房报告，其余房仍可独立成功。

## 稀疏结构与水景

两份压缩 NBT 按用户原件逐字节打包：

- `data/ftdungeonmobs/structures/rooms/31.nbt`：SHA-256 `d28d9a41b7a920c891546368f2d2a78c65ccc864b9e6741c77ecec880ca6bd82`。
- `data/ftdungeonmobs/structures/rooms/30_1.nbt`：SHA-256 `7fbebcac1a2fa99dad419a057f09b85c856e6f5005fc945adce1c44e0b7b35d0`。

未记录坐标不作为清空命令；31 的 5,655 个 `void_air` 记录保留原义。原生空区段可能将 `void_air` 读回为普通空气，校验仅对空气允许此语义等价，不放宽任何实方块或箱子状态。因为施工前要求整片区域为空，不需要挖掘或清除旧地形。31 含 2,082 格真实水，外沿有暴露水源，因此在模板外加 Y=64..68 的实心挡水边界；入口开口由连接地板阻挡外溢，不能将它当作无流体效果的装饰。

## Lootr 与玩法边界

- 31 包含 17 个 `lootr:lootr_chest`，目标服务端和客户端应有兼容 Lootr。缺失或非法方块/属性会在施工前拒绝，不静默降级成空气或普通箱子。
- Forge 隔离验证使用本机已有的 Lootr `1.20-0.7.35.94`，仅添加验证运行时依赖，不将其内嵌入 FT JAR，也不改变主模组已有前置要求。
- 17 个 Lootr 箱、3 个普通箱和3个潜影盒在原 NBT 中均为空、无战利品表；保留原样，不自作主张添加奖励。Lootr 运行时的其它配置仍由目标整合包决定。
- 没有增加自然刷怪、怪物波次、挑战结束或奖励逻辑。五档 FT 怪物难度仍沿用已有接口。独立的 FT 地牢挑战模组保持原安装/禁用状态。
- 原门的 6000 tick 队友入场窗口、锁定与返程机制未改。0.16.0 已记录的合法返程门占用误报仍属独立既有问题，本次不能宣称已修复多人连续入场。

## 安全与存档

生成标记在地牢维度 `data/ftdungeonmobs_rooms.dat`，原两间使用 `LayoutVersion=1`，九间目录使用独立的 `Rooms` 指纹列表；二者均独立于原入口轮次 SavedData。原世界没有相应标记时允许首次检查；更高布局版本不会因降级而被当成未生成。

先加载目标附近的正常区块，再完整预检，每组/间全部通过后才施工。不增加常驻强加载票据或持续扫描。首次进入需检查和放置十一间结构及道路，可能有明显短暂卡顿，未测量完整整合包实机 FPS；已生成房间不会重复加载放置。

同步放置失败时尝试恢复本次触及的原方块，不把失败写成生成完成。突然断电/进程崩溃不具备跨区块与 SavedData 的事务保证；若留下部分结构，下一次检查会拒绝覆盖，应由管理员核对并从备份恢复，而不是盲目清除占用区。

安装前关闭游戏/服务器并备份。完整重启后生效；多人两端使用同版，服务器也须有模板所需 Lootr。此次在外部工具中不打开或代执行玩家存档中的施工命令。回退请先完整备份世界和维度，不要删除玩家入口轮次或返回记录；已生成的房间主要由原版与 Lootr 方块组成，但降级后不再提供此扩建入口或状态命令。

## 验证入口

```powershell
.\BUILD.ps1 -Task verifyDungeonRooms -Offline
.\BUILD.ps1 -Offline
.\BUILD.ps1 -Task runData -Offline
.\BUILD.ps1 -Task runGameTestServer -Offline
```

静态校验检查原件哈希、方块记录、模板坐标不重叠与空容器。Forge 数据环境用真实原版/Lootr 注册表解析并读写模板，并验证尺寸、道路和地基、挡水边界、非法 NBT 拒绝及保存标记。GameTest 仅在工程内独立的 `run/rooms-gametest` 世界执行和清理测试区域，检查真实地牢中的占用/实体拒绝、全部 25,335 条方块记录、17 个 Lootr 方块实体和再次调用不覆盖玩家修改；不加载玩家存档，也不代表完整整合包多人实机验收。

九间额外使用 `DungeonRoomGalleryGameTests`，逐间核对模板、原生放置后状态与支撑、北开口/内部路径、实际共享道路净高、边界液体拒绝、实体拒绝、持久化、幂等和 40 tick 外溢检查。最终验收要求日志明确 `rooms=9/9`；仅部分房间通过不能替代全量证明。原图、实际 NBT 预览、交付指纹、最终坐标、验证日志与部署收据集中在 `D:/ft工程文件/FT地牢_Image25接入_20261101/integration/`。
